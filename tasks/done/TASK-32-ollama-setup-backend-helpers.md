# TASK-32: Backend helper commands for guided Ollama setup

## Goal
Three new typed Tauri commands exist and are reachable from the frontend: a reachability ping for Ollama, a model-presence check, and an external-URL opener. Each is registered in both the `invoke_handler` and the `tauri-specta` builder, and the regenerated `src/bindings.ts` includes their typed wrappers.

## Context
We're adding a guided setup flow for the Chaperone (Advanced) cleanup mode. The Modes tab Advanced panel will detect whether Ollama is reachable, whether the configured classifier model is pulled, and offer an "Install Ollama" button that opens https://ollama.com/download in the user's browser. This task delivers only the backend plumbing those UI elements depend on. The frontend UI itself, the long-running model-pull command, and the silent-fallback toast are out of scope here — they have their own tasks.

The three commands:

1. **`ping_ollama()`** — hits `GET {ollama_url}/api/version` with a 2-second connect+read timeout. Returns a small struct: `{ reachable: bool, version: Option<String> }`. The configured URL is read from `crate::settings::load().cleanup.ollama_url` and must pass the same loopback allowlist used by `validate_ollama_url` in `src-tauri/src/cleanup.rs` — re-export or reuse that helper, do not duplicate the logic. Any error (URL invalid, connect refused, timeout, non-2xx) returns `Ok(Reachable { reachable: false, version: None })` rather than `Err`, so the frontend can render the "not detected" state without bouncing through `typedError` for a normal expected case.

2. **`check_ollama_model(model_name: String)`** — hits `GET {ollama_url}/api/tags` with the same 2s timeout, parses the response, and returns `Ok(bool)` indicating whether `model_name` appears in the `models[].name` list. Ollama returns names like `llama3.2:3b` exactly as the user pulled them — match on full string equality, not prefix. Network failures or invalid URL return `Ok(false)` (same rationale as `ping_ollama`). Only a true panic-class error (e.g. JSON shape changed) should `Err`.

3. **`open_url(url: String)`** — opens the URL in the user's default browser. To avoid pulling in `tauri-plugin-shell`, implement directly with `std::process::Command`: `open <url>` on macOS, `cmd /c start "" <url>` on Windows, `xdg-open <url>` on Linux. Validate the URL: must parse as a `url::Url`, must use `https`, and must be in a host allowlist of `ollama.com` and any subdomain (`*.ollama.com`). This is intentionally narrow — the only call site this task enables is the "Install Ollama" button. Reject anything else with a clear `Err` so future misuse fails loudly rather than silently opening attacker-controlled links.

`tauri-specta` regenerates `src/bindings.ts` automatically when `cargo test export_bindings` runs (per AGENTS.md / README). The header at the top of `bindings.ts` documents the regen command. Don't hand-edit the TS file. Existing typed-command examples to mirror: `runDiagnostics`, `openSystemSettings`, `openDataFolder` — all in `src-tauri/src/lib.rs`.

The 2-second timeout pattern is already established in `cleanup.rs::classify_blocking` — `reqwest::blocking::Client::builder().timeout(...).connect_timeout(...)`. Reuse that exact construction for `ping_ollama` and `check_ollama_model` so the timeout behavior stays consistent. Do **not** apply a hard timeout to `open_url` — it just spawns a process and returns.

## In scope
- `src-tauri/src/cleanup.rs` — make `validate_ollama_url` `pub(crate)` if it isn't already, so the new commands can reuse it without copying the loopback allowlist
- A new module file, e.g. `src-tauri/src/ollama.rs`, holding the three command functions and a `Reachable` response struct (`#[derive(Serialize, specta::Type)]`). Keep `cleanup.rs` focused on its current job.
- `src-tauri/src/lib.rs` — `mod ollama;`, register the three commands in both the `tauri::generate_handler!` macro **and** the `tauri_specta::Builder::commands` list
- `src/bindings.ts` — regenerated by the test harness, not hand-edited

## Out of scope
- The streaming model-pull command (separate task: TASK-33)
- Any frontend UI changes (separate task: TASK-34)
- The silent-fallback ui-error toast (separate task: TASK-35)
- Adding `tauri-plugin-shell` or `tauri-plugin-opener`
- Loosening the URL allowlist beyond `*.ollama.com`
- Caching: every call hits the network. Polling/throttling lives in the frontend task.

## Steps
1. Read `src-tauri/src/cleanup.rs` for the existing `validate_ollama_url` helper, the 2s timeout pattern, and the `OLLAMA_TIMEOUT` constant. Note the loopback host allowlist.
2. Read `src-tauri/src/lib.rs` to find where commands are registered. Identify the `tauri::generate_handler!` macro call and the `tauri_specta::Builder::new().commands(collect_commands![...])` call. Both lists must be edited.
3. Read one existing typed-command example end-to-end (e.g. `run_diagnostics` in `src-tauri/src/diagnostics.rs`) to confirm the `#[tauri::command]` + `#[specta::specta]` attribute pair and the return-type conventions.
4. Create `src-tauri/src/ollama.rs`. Define the `Reachable` struct (`reachable: bool`, `version: Option<String>`) with `Serialize + specta::Type`. Implement the three commands. For `ping_ollama` and `check_ollama_model`, build a `reqwest::blocking::Client` with the 2s timeout, validate the URL via `cleanup::validate_ollama_url`, and short-circuit to the negative result on any expected failure (URL invalid, connect, timeout, non-2xx, JSON parse).
5. Wire `mod ollama;` into `lib.rs` and add the three commands to both registration lists. Order alphabetically with neighbors so diffs stay tidy.
6. Regenerate bindings: `cargo test --manifest-path src-tauri/Cargo.toml export_bindings`. Confirm `src/bindings.ts` now contains `pingOllama`, `checkOllamaModel`, `openUrl` and the `Reachable` type.
7. Build the backend: `cargo build --manifest-path src-tauri/Cargo.toml`. Must compile cleanly.
8. Smoke test by hand from the dev tools console once the app is running:
   - `await __TAURI_INVOKE('ping_ollama')` with Ollama down → `{ reachable: false, version: null }`
   - With Ollama up → `{ reachable: true, version: "0.x.y" }`
   - `await __TAURI_INVOKE('check_ollama_model', { modelName: 'llama3.2:3b' })` → `true`/`false` as appropriate
   - `await __TAURI_INVOKE('open_url', { url: 'https://ollama.com/download' })` → opens the page; `https://example.com` → returns an `Err`
9. Update `SESSION-STATUS.md` with one line: backend helpers for Ollama setup landed.

## Success signal
- `cargo build --manifest-path src-tauri/Cargo.toml` succeeds.
- `cargo test --manifest-path src-tauri/Cargo.toml export_bindings` exits 0 and `src/bindings.ts` shows `pingOllama`, `checkOllamaModel`, `openUrl` in the `commands` object plus the `Reachable` type export.
- The four hand-invocations from Step 8 all return the expected results in dev mode.
- `https://example.com` passed to `open_url` returns an `Err` (allowlist works).

## Notes
- If `reqwest` is already configured for `blocking` in `cleanup.rs` it's already a feature in `Cargo.toml`. Don't re-enable features that exist.
- The `version` field on `/api/version` is a simple `{"version":"x.y.z"}` shape. A single struct with `version: String` parsed from JSON is sufficient.
- The `/api/tags` response shape is `{"models":[{"name":"llama3.2:3b","modified_at":"...","size":...},...]}`. You only need `models[].name`. A minimal partial deserialize struct is fine.
- Keep error variants inside `Err` strings short and human-readable. The frontend will render them in toasts.
