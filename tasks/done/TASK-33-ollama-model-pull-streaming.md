# TASK-33: Backend Ollama model-pull streaming command

## Goal
A new typed Tauri command, `pull_ollama_model(model_name)`, downloads a model into the user's local Ollama instance by streaming `POST {ollama_url}/api/pull`, parses the NDJSON progress stream, and emits incremental `ollama-pull-progress` Tauri events to the frontend with `{ model: String, pct: u8, status: String }` payloads. The command resolves with `Ok(())` on stream completion (`status == "success"`) and `Err(message)` on any unrecoverable failure. It is registered in both the `invoke_handler` and `tauri-specta` builder, and the regenerated `src/bindings.ts` exposes it as `pullOllamaModel`.

## Context
The Modes tab Advanced (Chaperone) panel will offer a "Download classifier model (~2GB)" button when Ollama is reachable but the configured `classifier_model` (default `llama3.2:3b`) isn't pulled. Clicking it should mirror the existing whisper-model download UX: percentage + progress bar, ending in a green "Ready" pill. This task delivers only the backend side. The frontend wiring is TASK-34.

The Ollama streaming pull API:
- `POST {ollama_url}/api/pull` with JSON body `{ "model": "<name>", "stream": true }`
- Response is **newline-delimited JSON**, not a single JSON document. Each line is a status update like:
  - `{"status":"pulling manifest"}`
  - `{"status":"pulling abc123","digest":"sha256:abc...","total":1234567890,"completed":50000000}`
  - `{"status":"verifying sha256 digest"}`
  - `{"status":"writing manifest"}`
  - `{"status":"removing any unused layers"}`
  - `{"status":"success"}` ← final line on completion
- The pull can take several minutes for a multi-GB model. **No hard timeout** on this call (this is the explicit exception to the 2s pattern used elsewhere). A `connect_timeout` of a few seconds is fine — the connect itself shouldn't be slow on loopback — but the read timeout must be effectively unbounded.

The same loopback URL allowlist enforced by `validate_ollama_url` in `src-tauri/src/cleanup.rs` applies. Do not duplicate the function — `cleanup::validate_ollama_url` should be `pub(crate)` after TASK-32 lands.

The progress-event pattern is already established for whisper models. Read `src-tauri/src/lib.rs` and `src-tauri/src/whisper_models.rs` (or wherever `download_model` lives) for the exact `app_handle.emit("download-progress", payload)` shape and the matching frontend listener in `src/App.svelte` (search for `download-progress` to find both ends). Mirror that pattern with a different event name, `ollama-pull-progress`, and a payload that includes the model name (the frontend will key its progress map on it).

The percentage is computed from the streaming `total` and `completed` fields. Multiple layers can pull in sequence, each reporting its own `total` and `completed`. **Compute pct only when both fields are present and `total > 0`**. Status lines without those fields ("pulling manifest", "verifying", "success") emit a progress event with the current `status` string and either the last-known pct or `0`. Don't reset to 0 on transitional statuses — clamp to "max pct seen so far" so the bar only ever moves right.

Cancellation is **out of scope** for this task. The user clicks once, waits, sees progress. We can add cancel later if it matters.

`reqwest::blocking::Client` with `.send().bytes_stream()` is wrong — that's the async API. For blocking streaming use `Response::read` or wrap the reader in a `BufReader` and `read_line` loop. The async approach (`tokio::spawn` + `reqwest` async + `bytes_stream`) is also acceptable if the rest of the file uses async; pick whichever is consistent with the existing whisper download command.

## Steps
1. Read the existing whisper-model download command end-to-end (start with `src-tauri/src/lib.rs`, grep for `download_model` and `download-progress`). Note the `AppHandle` injection, the event payload struct, and how the frontend listener consumes it.
2. Read `cleanup.rs::validate_ollama_url` — confirm visibility (must be `pub(crate)` after TASK-32) and reuse it as-is.
3. In `src-tauri/src/ollama.rs`, define the progress payload struct (e.g. `OllamaPullProgress { model: String, pct: u8, status: String }`) with `Serialize + specta::Type`.
4. Implement `pull_ollama_model(app: AppHandle, model_name: String) -> Result<(), String>`:
   - Validate `cleanup.ollama_url` via `validate_ollama_url`.
   - Build a `reqwest::blocking::Client` with a connect timeout but **no** read timeout (`Duration::MAX` or `None` — match the pattern used by the whisper download).
   - Send `POST {url}/api/pull` with body `{"model": model_name, "stream": true}`.
   - Wrap the response body in a `BufReader` and iterate `read_line`. Each non-empty line: `serde_json::from_str` into a partial struct with optional `status: String`, `total: Option<u64>`, `completed: Option<u64>`.
   - Compute pct from `(completed * 100) / total` when both present and `total > 0`; otherwise keep the last pct. Clamp to monotonic non-decreasing.
   - Emit `app.emit("ollama-pull-progress", OllamaPullProgress { model: model_name.clone(), pct, status })`. Don't emit faster than ~10 Hz — coalesce updates within a 100ms window if the layer is small enough to spam them.
   - On `status == "success"` line, return `Ok(())`. On JSON parse error of an individual line, log via `tracing::warn!` and continue (the next line is probably fine). On stream/IO error, return `Err(message)`.
5. Register in `lib.rs`: `mod ollama;` already exists from TASK-32; add `ollama::pull_ollama_model` to both `generate_handler!` and `tauri-specta` builder lists.
6. Regenerate bindings: `cargo test --manifest-path src-tauri/Cargo.toml export_bindings`. Confirm `pullOllamaModel` and `OllamaPullProgress` appear in `src/bindings.ts`.
7. Build: `cargo build --manifest-path src-tauri/Cargo.toml`. Must compile.
8. Smoke test in dev mode with Ollama running and the configured model **not** already pulled:
   - From the dev-tools console, attach a listener:
     `await window.__TAURI__.event.listen('ollama-pull-progress', e => console.log(e.payload))`
   - Trigger the pull:
     `await __TAURI_INVOKE('pull_ollama_model', { modelName: 'tinyllama' })` (use a small model for the smoke test, not the 2GB default)
   - Observe a stream of payloads with monotonic `pct`, ending in `status: "success"` and the call resolving Ok.
9. Update `SESSION-STATUS.md` with one line.

## Success signal
- `cargo build` and `cargo test export_bindings` both succeed.
- `pullOllamaModel` appears in `src/bindings.ts` as a typed function returning `Promise<{status:"ok",data:null}|{status:"error",error:string}>`.
- During the smoke-test pull, the dev-tools console logs a sequence of `ollama-pull-progress` events with `pct` values that never decrease and a final `status: "success"`.
- The same call against an Ollama instance that's not running returns `Err` within a few seconds (connect failure surfaces as a clean error string).

## Notes
- `tinyllama` is ~640MB and pulls in ~30s on a fast connection — good for hand-testing. Don't paste the multi-GB default into smoke tests.
- The Ollama HTTP API docs: `POST /api/pull` returns NDJSON when `stream: true`. Confirm the exact field names from a real captured response if anything doesn't match: `curl http://localhost:11434/api/pull -d '{"model":"tinyllama","stream":true}'`.
- The throttle (Step 4: ≤10 Hz) is so the IPC bridge doesn't choke on a fast pull. A simple "remember last-emitted ts and skip if <100ms ago, but always emit on layer-end / status-change" is enough.
- Keep `Err(String)` messages short — they bubble to the frontend and may end up in toasts.
